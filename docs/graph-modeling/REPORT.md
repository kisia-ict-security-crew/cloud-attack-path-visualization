# CloudTrail 행위 로그의 그래프 모델링과 공격 기법의 부분그래프 표현

> 연구 요약 — 논문 작성용. 최신(6-로그) 결과만 담는다. 모델·뷰의 상세 정의는
> `3-node-v2.md`, `enrich.md`, `query.md` 참조.

---

## 초록

AWS CloudTrail 로그(실제로 일어난 API 호출 기록)를 그래프로 변환해, 클라우드
공격 경로를 분석 가능한 형태로 만든다. 정적 IAM 설정을 그래프화하는 기존 도구와
달리 **실제 행위**를 그래프화하며, 특정 공격에 특화되지 않은 **목적 중립적 기반
그래프** 위에 목적별 해석을 **뷰**로 얹는 2계층 구조를 취한다. Stratus Red Team
6개 공격 기법(661 이벤트)에 대해, (i) 공격 기법을 API 이름이 아닌 **부분그래프
모티프**로 정의해 5개 중 5개를 식별했고, (ii) 필드 절제 실험으로 **최소 스키마**를
측정했다 — 정규식 2개로 5개 중 4개가 잡히고, 단일 필드 `readOnly` 가 4개를
좌우한다.

---

## 1. 배경·문제

CloudTrail 레코드 하나에는 수십 개 필드가 있고 `requestParameters` 는 API 마다
구조가 다르다. 그래프로 옮길 때 "무엇을 남길 것인가"에 원칙이 없으면 새 로그가
들어올 때마다 파서에 예외를 덧붙이게 된다. 동시에, 그래프로 만든 것이 단순
시각화에 그치면 "왜 그래프여야 하는가"에 답하지 못한다.

두 물음을 함께 다룬다.

- **표현력**: 클라우드 공격 기법을 그래프 질의(부분그래프 모티프)로 표현할 수
  있는가. API 이름 목록(=탐지 룰)이 아니라 구조로.
- **최소성**: 그 표현에 실제로 필요한 로그 필드는 무엇인가. 측정으로 답한다.

---

## 2. 방법

### 2.1 기반 모델 (상세: `3-node-v2.md`)

모든 노드가 공통 라벨 `:Node` 를 갖고 `id` 가 유일 키다. 그 위에 역할 라벨
**`:Actor` / `:Resource` / `:Service`** 를 하나 이상 가진다(겸직 정상). 엣지는
두 종류다.

- **`:BASE_EVENT`** — 시각이 있는 단일 API 호출. `actionL2`(의도: READ/CREATE/
  MODIFY/DELETE/ASSUME/EXECUTE), `outcome`, `errorClass`, `readOnly`, `sourceIP`
  등을 속성으로 갖는다. 이벤트 하나가 대상 N개면 N개 엣지.
- **`:CONTEXT`** — 여러 이벤트에 걸쳐 성립하는 사실. `ISSUES`(신원→키: 이 키가
  어느 신원의 것인가), `RUNS_ON`(키→워크로드). 키가 **쓰인** 이벤트의
  `userIdentity` 에서 재구성한다 — 발급 이벤트가 아니라 사용 흔적이 근거라
  IAM 사용자·Role·root 등에 대칭으로 적용된다(외부 IdP 세션 제외 — §4).

핵심 설계 판단 셋:

1. **주체 id = `accessKeyId`** (ARN 아님). `arn→accessKeyId` 가 1:N 이라, ARN 을
   PK 로 쓰면 같은 신원이 다른 IP·다른 키로 쓰인 신호가 소멸한다. 대신 한 IAM
   신원이 **행위할 때는 키 노드, 대상이 될 때는 ARN 노드**로 갈리는데, `ISSUES`
   가 이 둘을 이어 "백도어 사용자 생성 → 그 키의 후속 행위" 같은 사슬을 연결한다.
2. **`actionL2`(의도)와 `outcome`(결과) 분리.** 실패한 `DeleteBucket` 이
   `DELETE`+`FAILURE` 로 남아 "삭제 시도 전부"가 질의된다.
3. **무손실 포기, `eventID` 로 원본 조인.** 그래프는 골격만, 포렌식 상세는 원본
   JSON. 그래프가 원본의 24%로 줄어든다.

### 2.2 뷰 계층 (상세: `enrich.md`)

기반에는 판단이 없다. 뷰는 두 가지만 한다 — **(A) 분류**(있는 것에 라벨·속성을
단다, 새 정보 없음)와 **(B) 합성**(기반에 없는 관계 하나를 새로 잇는다).

- **종류 라벨** `:Credential`/`:Identity`/`:Workload`/`:Asset` — 노드당 하나.
  "AWS 가 뭐라 부르는가"가 아니라 "이 그래프에서 무슨 역할을 하는가" 기준.
- **`advances`** — `BASE_EVENT` 에 도달 전이 여부(불리언). `outcome=SUCCESS` ∧
  대상특정 ∧ (자격증명 획득 또는 `readOnly=false`)면 true. 공격 경로 순회가
  따라갈 엣지를 이 하나로 고른다 — `readOnly` 하나가 전이/조회를 가른다.
- **`:CAN_OBTAIN`** (합성) — "주체가 워크로드를 장악" × "그 워크로드에 키가 실림"
  두 홉을 접어 "주체가 그 키를 얻을 수 있다"를 잇는다. **탈취 행위는 로그에
  엣지로 존재하지 않으므로**(기반에 이 쌍의 엣지가 0개) 이 합성이 필요하다.
  `exercised` 속성으로 주체 IP 와 키 사용 IP 가 겹치는(=실제 행사 흔적) 것을 표시.

### 2.3 공격 모티프 (상세: `query.md`, `motifs.py`)

기법을 **부분그래프 모양**으로 정의한다. 정답은 각 기법의 상세 문서
"결정적 이벤트"에서 도출했다(파서 출력이 아니라 기법 설명에서 — 순환 논리 회피).

| 모티프 | 기법 | MITRE | 모양 | API 이름 |
| :--- | :--- | :--- | :--- | :---: |
| M1 자격증명 탈취 | ec2-steal-instance-credentials | T1552.005 | 남의 워크로드 장악 + 그 키가 같은 IP 에서 쓰임 | 없음 |
| M2 측면 이동 | ec2-instance-connect | — | 한 주체가 남의 워크로드 둘 이상에 접근 주입 | 없음(서비스명) |
| M3 유출 | ec2-share-ebs-snapshot | — | 저장 자산이 CREATE→MODIFY→DELETE | 없음 |
| M4 방어 회피 | cloudtrail-delete + vpc-remove-flow-logs | T1562.008 | 관측 자산(트레일·플로우로그) 삭제 | 없음 |
| M5 지속성 | iam-backdoor-user | T1098 | 남의 신원에 만료 없는 키 발급 | 없음 |

**5개 중 4개가 API 이름을 전혀 쓰지 않는다.** M2 만 서비스 목록을 쓴다.

## 3. 결과

### 3.1 데이터셋·파싱·검증

Stratus Red Team 6개 기법, 총 661 이벤트. 단일 계정, 시간대 비중첩.

| 데이터셋 | MITRE | 이벤트 | 노드 | BASE_EVENT | 미해결% | CONTEXT |
| :--- | :--- | ---: | ---: | ---: | ---: | ---: |
| ec2-steal-instance-credentials | T1552.005 | 183 | 47 | 238 | 4.6% | 11 |
| ec2-instance-connect | — | 302 | 51 | 383 | 3.9% | 18 |
| ec2-share-ebs-snapshot | — | 20 | 5 | 21 | 14.3% | 1 |
| cloudtrail-delete | T1562.008 | 56 | 20 | 62 | 19.4% | 5 |
| vpc-remove-flow-logs | T1562.008 | 63 | 30 | 83 | 15.7% | 8 |
| iam-backdoor-user | T1098 | 37 | 17 | 40 | 27.5% | 4 |
| **통합** | | **661** | **123** | **827** | **7.9%** | **39** |

- 개별 노드 합 170 → 통합 123. **노드가 로그 간 공유되기 때문**(운영자 키 등
  6개 전부에 공통). 통합이 단순 이어붙이기가 아니라는 근거.
- 원본 JSON 1,056KB → CSV 257KB (**24%**). 그래프 변환은 데이터를 줄인다.
- **필드 정확성 검증**(`verify_fields_v2.py`, 26개 검사): 6개 데이터셋 전부 통과.
  `refPath` 를 원본 JSON 에서 되짚어 경로가 실재하고 값이 대상 노드로 이어지는지,
  봉투 필드가 원본과 일치하는지, 배치 API 부분 실패가 대상별로 갈리는지를 확인.

**뷰 계층 분포**(통합): 도달 전이 `advances` = true 263 / false 564
(false 내역은 base 속성으로 — 조회 405 · 실패 98 · 미특정 61). 종류 라벨 =
Asset 73 / Credential 34 / Identity 12 / Workload 4.
`CAN_OBTAIN` 9개 중 `exercised` 1개(= ground truth).

### 3.2 모티프 재현

6개 기법 모두 부분그래프 모티프로 식별됐다(정답 대비 정확 일치).

| 모티프 | 정답 | 결과 |
| :--- | :--- | :--- |
| M1 | 탈취 쌍 1 | ○ 1 (오탐 0) |
| M2 | 팬아웃 1 (워크로드 3개) | ○ 1 |
| M3 | 스냅샷 1 | ○ 1 |
| M4 | 삭제 2 (트레일 1 + 플로우로그 1) | ○ 2 |
| M5 | 발급 1 | ○ 1 |

**M4 가 서로 다른 두 기법·두 API 를 한 모양으로 잡는다** — `DeleteTrail` 과
`DeleteFlowLogs` 는 서비스도 API 도 다르지만 "관측 자산을 지운다"는 구조가 같다.
룰 목록으로는 두 줄이 필요한 것을 그래프에서는 한 질의로 끝낸다. 이것이
"왜 그래프인가"에 대한 정량적 답이다 — 모티프는 그래프 질의고 룰 목록은 아니다.

M1 은 특히 **가능성과 사실을 분리**해 보인다. `CAN_OBTAIN`(가능성) 9개 중
`exercised`(주체 IP 와 키 사용 IP 일치) 1개만 남고, 그게 정확히 ground truth 다.

### 3.3 최소 스키마 절제 실험

필드를 하나씩 꺼가며 모티프 재현율을 측정했다(`ablate.py`).

**축 A — 대상 추출 강도** (그래프의 대상 노드를 얼마나 찾는가)

| 레벨 | 방법 | 미해결% | CSV | M1 | M2 | M3 | M4 | M5 |
| :--- | :--- | ---: | ---: | :-: | :-: | :-: | :-: | :-: |
| L0 | `resources[]` 만 | 77.0% | 141K | ○ | ✗ | ✗ | ✗ | ○ |
| L1 | + ARN·AWS id 정규식 | 14.4% | 226K | ○ | ○ | ○ | ✗ | ○ |
| L2 | + 핵심 이름 키 6개 | 8.1% | 235K | ○ | ○ | ○ | ✗ | ○ |
| L3 | + 전체 화이트리스트 50개 | 6.9% | 244K | ○ | ○ | ○ | ○ | ○ |

**정규식 2개(L1)만으로 5개 중 4개가 잡힌다.** 화이트리스트 50개가 추가로 잡는
것은 M4 하나뿐이고, 그마저 규칙 한 줄(트레일을 `requestParameters.name` 맨 키로
지정) 때문이다. "API 마다 추출 규칙을 늘려야 한다"는 압박은 근거가 없다 —
값의 형태로 잡는 규칙(정규식)은 API 개수와 무관하게 고정이다. 반면 L0(`resources[]`
만)는 명확히 부족하다(미해결 77%).

**축 B — 필드 하나씩 빼기 (leave-one-out, L3 기준)**

| 깨지는 모티프 수 | 필드 |
| ---: | :--- |
| **4** | `readOnly` (M1·M2·M3·M4) |
| 1 | `sourceIP` (M1) · `RUNS_ON` (M1) · `OBTAINS` (M5) · `responseElements` (M3) |
| **0** | `ISSUES` · `errorClass` · `resources[]` · `refPath` |

**단일 필드 `readOnly` 가 5개 중 4개를 좌우한다.** AWS 가 모든 이벤트에 붙여주는
불리언 하나가 "전이(advances=true) vs 조회"를 가르고, 네 모티프가 그 위에
선다. 그다음은 관계 필드(`RUNS_ON`, `OBTAINS`) — 각각 한 모티프의 전제라 빠지면
그 기법이 통째로 사라진다. 0-기여 필드를 다 빼면 CSV 17% 감소, 재현율 동일.

**"0-기여 = 무용"은 아니다.** `errorClass` 는 권한 정찰(`errorClass=DENIED`)의,
`refPath` 는 "대상 vs 질의조건" 판단을 뷰로 미루는 근거이며, `ISSUES` 는
자격증명을 그 소유 신원으로 되짚어("백도어 사용자 → 그 키의 후속 행위") 다단계
사슬을 잇는다. 이 5개 모티프가 안 쓸 뿐이다. 실험이 주는 규율은 "필드를 지워라"가 아니라 **새 필드를 넣을 때
'로그에 있는가'가 아니라 '어떤 모티프가 이것을 요구하는가'를 묻는 것**이다.

## 4. 한계

- **정답이 기법당 1~2건이라 재현율이 계단함수다.** 통계적 의미는 약하며, 이
  결과는 "방법이 성립하는가"를 보인 파일럿이다. 기법 표본을 늘려야 곡선이 나온다.
- **단일 계정·합성 로그·짧은 시간 구간.** 실제 침해에서는 warmup 과 detonate 를
  같은 주체가 하지 않고 노이즈 규모도 다르다. 특히 M1 의 IP 일치 조건은 공격자가
  다른 단말·프록시를 쓰면 성립하지 않는다.
- **크로스 계정 유출의 수신 계정이 그래프에 없다.** `ModifySnapshotAttribute` 의
  외부 계정 `userId` 를 파서가 수집하지 않아, "권한을 열었다"까지만 보이고
  "누구에게"는 안 보인다.
- **외부 IdP 페더레이션 세션은 소유 신원과 못 잇는다.** `ISSUES` 는 자격증명을
  그 신원(IAM 사용자·Role·root)으로 되짚지만, SAML/WebIdentity 세션은 소유자가
  외부 IdP(예: `accounts.google.com`)라 결합할 AWS ARN 노드가 없다. 또한 발급만
  되고 한 번도 쓰이지 않은 키는 사용 흔적이 없어 `ISSUES` 가 안 생긴다(발급 사실
  자체는 `OBTAINS` 에 남는다). 6개 데이터셋에는 두 경우 모두 해당 사례가 없다.
- **모티프가 자격증명·워크로드 중심 기법에 치우쳐 있다.** 6개에서 도출했고,
  데이터·네트워크 계층 기법은 다루지 않았다.
- **순환 논리를 완전히 제거하지 못했다.** 모티프를 기법 문서에서 도출했으나 그
  문서 자체가 같은 로그를 보고 쓰였다. 모티프를 먼저 고정하고 새 로그를 나중에
  생성하는 다단계(APT) 체인 로그가 다음 단계다.
